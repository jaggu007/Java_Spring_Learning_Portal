Building a PUT API

Replace a resource at a known URI with Spring Boot, validated input, deliberate persistence, and correct HTTP semantics.

← Previous: POST API Unit 5 Home Next: DELETE API →

Learning outcomes

After this lesson, you should be able to explain PUT semantics, design a complete replacement request, implement a validated Spring Boot endpoint, distinguish create/update status responses, and test missing-resource and concurrency behavior.

PUT represents replacement at a known URI. It is idempotent by definition: repeating the same request has the same intended effect. If the API supports partial changes, design a PATCH operation instead of treating omitted PUT fields ambiguously.

1. PUT and resource replacement

A client sends a representation to a known resource URI, such as PUT /api/courses/42. The server applies the representation as the new state of that resource. A PUT request should be designed as a complete replacement for the fields defined by that representation, not an informal partial update.

2. Choose a clear update contract

For an existing resource, a successful replacement commonly returns 200 OK with the updated representation or 204 No Content without a body. HTTP also permits PUT to create a resource at the target URI when the server’s contract supports it; many APIs instead require the resource to exist and return 404 Not Found if it does not. Choose and document one behavior.

4. Define a complete replacement DTO

For PUT, the request should contain all client-managed fields that make up the replaceable representation. In this example, code, title, and credits are required. The server-managed ID is not included in the body because it is already identified by the URI.

package com.example.course.dto;

import jakarta.validation.constraints.Max;
import jakarta.validation.constraints.Min;
import jakarta.validation.constraints.NotBlank;
import jakarta.validation.constraints.Size;

public record ReplaceCourseRequest(
        @NotBlank
        @Size(max = 20)
        String code,

        @NotBlank
        @Size(max = 120)
        String title,

        @Min(1)
        @Max(6)
        int credits
) {}

With a primitive int, a missing JSON field can become the default value 0 and fail @Min(1). If distinguishing omitted values from explicit values matters, use a nullable wrapper or a custom deserialization/validation strategy. For PATCH, model partial input separately.

5. Replace the resource in the service

The service loads the current resource, enforces update rules, applies the complete replacement, and returns the resulting response DTO. A missing resource follows the API’s documented policy.

@Service
public class CourseService {
    private final CourseRepository repository;

    public CourseService(CourseRepository repository) {
        this.repository = repository;
    }

    @Transactional
    public CourseResponse replace(
            long id, ReplaceCourseRequest request) {
        Course course = repository.findById(id)
                .orElseThrow(() -> new CourseNotFoundException(id));

        course.setCode(request.code().trim());
        course.setTitle(request.title().trim());
        course.setCredits(request.credits());

        Course saved = repository.save(course);
        return toResponse(saved);
    }

    private CourseResponse toResponse(Course course) {
        return new CourseResponse(
                course.getId(),
                course.getCode(),
                course.getTitle(),
                course.getCredits());
    }
}

This example assumes a mutable JPA entity with setters and a repository that provides findById and save. A managed entity inside a transaction may be persisted through dirty checking; an explicit save is shown for clarity.

Do not change immutable fields such as a resource’s ownership or creation timestamp merely because they appear in the request. Define which fields PUT replaces and enforce authorization before applying changes.

6. Implement the Spring controller

Use @PutMapping for the target URI and @Valid @RequestBody for the complete replacement representation.

@RestController
@RequestMapping("/api/courses")
public class CourseController {
    private final CourseService courseService;

    public CourseController(CourseService courseService) {
        this.courseService = courseService;
    }

    @PutMapping("/{id}")
    public ResponseEntity<CourseResponse> replaceCourse(
            @PathVariable long id,
            @Valid @RequestBody ReplaceCourseRequest request) {
        CourseResponse updated =
                courseService.replace(id, request);
        return ResponseEntity.ok(updated);
    }
}

This update-only endpoint returns 200 OK with the updated resource and throws a not-found exception when the ID does not exist. A shared @RestControllerAdvice should map that exception to 404 and validation exceptions to a safe 400 response.

Do not implement PATCH by accepting a nullable DTO without defining the meaning of absent versus explicit null. If supporting JSON Merge Patch or JSON Patch, document the media type and exact patch semantics.

8. Concurrent updates and lost-update protection

Two clients can read the same version and then overwrite each other’s changes. If lost updates matter, use optimistic locking or HTTP preconditions instead of relying on request ordering.

Optimistic locking with JPA

@Version
private long version;

With a version field, the persistence provider detects a conflicting update and raises an optimistic-locking failure. Map it to a documented conflict response. Alternatively, expose an ETag and require an appropriate If-Match value; a stale precondition can return 412 Precondition Failed.

Idempotent does not mean conflict-free. PUT can be idempotent while still needing concurrency control to prevent one client from unknowingly overwriting another client’s newer state.

9. Test the PUT contract

Test the successful replacement, missing-resource behavior, malformed or invalid input, and concurrency conflicts when supported.

mockMvc.perform(put("/api/courses/42")
        .contentType(MediaType.APPLICATION_JSON)
        .accept(MediaType.APPLICATION_JSON)
        .content("""
            {"code":"CS336B","title":"OOPS with Java","credits":4}
            """))
    .andExpect(status().isOk())
    .andExpect(jsonPath("$.id").value(42))
    .andExpect(jsonPath("$.title").value("OOPS with Java"));

mockMvc.perform(put("/api/courses/999")
        .contentType(MediaType.APPLICATION_JSON)
        .content("""
            {"code":"CS999","title":"Missing Course","credits":3}
            """))
    .andExpect(status().isNotFound());

Also test that omitted fields follow the documented PUT contract, and that unauthorized callers cannot replace resources they do not own.

10. Call the endpoint

curl -i \
  -X PUT http://localhost:8080/api/courses/42 \
  -H "Content-Type: application/json" \
  -H "Accept: application/json" \
  -d '{"code":"CS336B","title":"OOPS with Java","credits":4}'

For the update-only example, a successful call returns 200 OK and the updated JSON representation. The same complete request can be sent again without changing the intended final state.

11. Security and reliability

  • Authorize by resource: check that the caller may modify this specific ID; do not rely only on authentication.
  • Use a narrow DTO: never let the client set ownership, roles, IDs, or audit metadata unless explicitly authorized.
  • Validate all replaceable fields: reject missing or invalid values according to the declared full-replacement contract.
  • Keep database constraints: validate business rules in the service and enforce invariants in the database where applicable.
  • Protect against lost updates: use versioning or conditional requests for shared mutable resources.
  • Use HTTPS and avoid logging full request bodies: update payloads may contain personal or confidential data.

Interview questions

  1. What does PUT mean in a REST API?
    Replace the state of a resource at a known target URI with the submitted representation.
  2. Is PUT idempotent?
    Yes, its intended effect is idempotent: repeating the same request should leave the resource in the same intended state.
  3. What is the difference between PUT and PATCH?
    PUT represents replacement; PATCH applies a partial modification with explicitly defined patch semantics.
  4. What should an update-only PUT return for a missing ID?
    Usually 404 Not Found, if the API contract requires the resource to exist.
  5. How can an API prevent lost updates?
    Use optimistic locking, an ETag with If-Match, or another explicit concurrency-control strategy.
  6. Why use a request DTO?
    It defines the replaceable fields and prevents clients from modifying server-managed data by mass assignment.
