Spring Boot Runners

Run controlled initialization logic after the Spring application context is ready and before the application reports itself as ready.

← Previous: Code Structure Unit 5 Home Next: Logger →

Learning outcomes

By the end of this lesson, you should be able to explain when Spring Boot runners execute, select between the two runner interfaces, read command-line arguments, define deterministic runner order, and avoid common startup-task problems.

Key point: A runner is a Spring bean whose callback is invoked during application startup after the context has been refreshed. It is suitable for short startup tasks, not for long-running work that should be detached from startup.

1. Where runners fit in the startup lifecycle

At a high level, Spring Boot prepares the environment, creates and refreshes the application context, instantiates required beans, and starts an embedded web server for a web application. Once the context has been refreshed, it invokes registered ApplicationRunner and CommandLineRunner beans. After the runners complete, the application publishes its ready event, such as ApplicationReadyEvent.

  1. Spring Boot prepares the application environment and context.
  2. Beans are created and dependency injection is performed; auto-configuration contributes applicable beans.
  3. The application context is refreshed. For a web application, the embedded server is started as part of web-context initialization.
  4. Runner callbacks execute in their configured order.
  5. After successful startup callbacks, Spring Boot signals that the application is ready.

Runners execute on the startup thread. If a runner blocks or takes a long time, application startup and readiness are delayed. An exception that escapes a runner is a startup failure; it is not silently treated as a successful start.

2. The two runner interfaces

InterfaceCallbackArguments providedUse when
CommandLineRunnerrun(String... args)Raw command-line argument stringsYou want to inspect or process the original argument list.
ApplicationRunnerrun(ApplicationArguments args)Parsed options and non-option argumentsYou want convenient access to option names, values, and non-option arguments.

Both are functional interfaces and can be registered as beans. Implement one or both according to what the task needs. If both types are present, Spring Boot invokes both according to their order; do not rely on an assumed order when it matters—configure and test it.

3. Using CommandLineRunner

The callback receives the application arguments as passed to the Java process. For example, with java -jar app.jar --mode=demo input.csv, the runner receives both strings, including the option string as written.

package com.example.course.startup;

import org.slf4j.Logger;
import org.slf4j.LoggerFactory;
import org.springframework.boot.CommandLineRunner;
import org.springframework.stereotype.Component;

@Component
public class StartupSummary implements CommandLineRunner {
    private static final Logger log =
            LoggerFactory.getLogger(StartupSummary.class);

    @Override
    public void run(String... args) {
        log.info("Application started with {} argument(s)", args.length);
    }
}

Use a logger rather than printing to standard output in a real application so output can be filtered and routed through the configured logging system. Avoid logging sensitive command-line values.

4. Using ApplicationRunner

ApplicationArguments separates option arguments (for example --mode=demo) from non-option arguments (for example input.csv). It also provides access to option names and all values supplied for an option.

package com.example.course.startup;

import org.slf4j.Logger;
import org.slf4j.LoggerFactory;
import org.springframework.boot.ApplicationArguments;
import org.springframework.boot.ApplicationRunner;
import org.springframework.stereotype.Component;
import com.example.course.service.ImportService;

@Component
public class ImportStartupTask implements ApplicationRunner {
    private static final Logger log =
            LoggerFactory.getLogger(ImportStartupTask.class);

    private final ImportService importService;

    public ImportStartupTask(ImportService importService) {
        this.importService = importService;
    }

    @Override
    public void run(ApplicationArguments args) {
        if (args.containsOption("import")) {
            log.info("Import option supplied; starting import task");
            importService.importFiles(args.getNonOptionArgs());
        }

        if (args.containsOption("mode")) {
            log.info("Mode values: {}", args.getOptionValues("mode"));
        }
    }
}

Run it with arguments such as:

java -jar course-api.jar --import --mode=demo input.csv
  • containsOption("import") checks whether that option is present.
  • getOptionNames() returns the option names.
  • getOptionValues("mode") returns values associated with an option; an option may have more than one value.
  • getNonOptionArgs() returns arguments that are not option arguments.
  • getSourceArgs() provides the original source argument strings.

Argument parsing is not a replacement for validation. If a startup command requires an option, validate that it exists and that its value is valid, then fail with a clear error if it is not.

5. Registering a runner with @Bean

Use a @Bean method when the runner is small or when you want to configure it alongside other application beans. Constructor injection also works naturally for runner classes registered with @Component.

package com.example.course.config;

import com.example.course.service.ReferenceDataService;
import org.springframework.boot.ApplicationRunner;
import org.springframework.context.annotation.Bean;
import org.springframework.context.annotation.Configuration;

@Configuration
public class StartupConfiguration {
    @Bean
    ApplicationRunner loadReferenceData(ReferenceDataService service) {
        return args -> service.ensureReferenceDataAvailable();
    }
}

The method parameter is injected by Spring. The runner is managed as a bean, so it can use other services through dependency injection rather than constructing dependencies itself.

6. Ordering multiple runners

When startup work must happen in a specific sequence, give runner beans an explicit order. Lower order values run before higher values. You can use @Order or implement Spring’s Ordered contract.

import org.springframework.boot.ApplicationRunner;
import org.springframework.context.annotation.Bean;
import org.springframework.context.annotation.Configuration;
import org.springframework.core.annotation.Order;

@Configuration
class StartupTasks {
    @Bean
    @Order(1)
    ApplicationRunner validateConfiguration() {
        return args -> System.out.println("Validate required configuration");
    }

    @Bean
    @Order(2)
    ApplicationRunner initializeApplication() {
        return args -> System.out.println("Initialize application state");
    }
}

Ordering is only meaningful when the work has a real dependency. Prefer one cohesive startup operation that calls its steps in order over unrelated beans coupled through implicit sequencing. Do not depend on bean discovery order.

7. Appropriate uses and alternatives

RequirementPossible approachConsiderations
Validate required configuration and fail fastRunnerKeep validation quick and report actionable errors.
Load small, idempotent reference dataRunner or database migration toolUse a migration system for schema changes and durable versioned data migrations.
Run a one-off command and exitRunner plus explicit application lifecycle managementA web application may keep its server alive; do not assume a runner automatically makes the process exit.
React to successful application readinessApplicationReadyEvent listenerUse an event listener when event semantics are clearer than a runner callback.
Perform a slow or recurring jobQueue, scheduler, or managed background workerDo not block application readiness with unbounded work.
Initialize every database instance safelyDatabase migration tool or idempotent initializationAccount for multiple application replicas starting concurrently.

8. Reliability, idempotency, and errors

  • Keep startup bounded: readiness should not wait on a long import, external crawl, or indefinite retry loop. Move substantial work to an asynchronous job or queue and expose its status.
  • Make repeatable work idempotent: deployments restart and scale out. A runner that inserts records on every startup can create duplicates. Use unique constraints, upserts, migrations, or an explicit completion record.
  • Plan for multiple replicas: each application instance runs its own runner. A database-backed task may need a migration tool, distributed lock, or another coordination mechanism if it must execute once across the deployment.
  • Handle failures deliberately: if the application must not serve traffic without successful initialization, allow failure to stop startup and log useful context. If the task is optional, record the failure clearly and define a recovery mechanism.
  • Use bounded external calls: configure connection and read timeouts for network or database work; avoid indefinite startup hangs.
  • Do not assume transactional behavior: a runner callback is not automatically one transaction. Put transactional operations in a suitable proxied service method and consider partial completion and retry behavior.
  • Do not use runners for secrets or credentials: avoid printing raw arguments or sensitive configuration to logs.

9. Testing runner logic

Keep business logic in a service and let the runner coordinate the startup call. This makes the service independently unit-testable and keeps the runner thin. A runner’s argument-handling behavior can also be tested directly.

      import static org.mockito.Mockito.verify;

import java.util.List;
import org.junit.jupiter.api.Test;
import org.junit.jupiter.api.extension.ExtendWith;
import org.mockito.InjectMocks;
import org.mockito.Mock;
import org.mockito.junit.jupiter.MockitoExtension;
import org.springframework.boot.DefaultApplicationArguments;

@ExtendWith(MockitoExtension.class)
class ImportStartupTaskTest {
    @Mock
    ImportService importService;

    @InjectMocks
    ImportStartupTask runner;

    @Test
    void importsNonOptionArgumentsWhenImportOptionIsPresent()
            throws Exception {
        var args = new DefaultApplicationArguments(
                "--import", "input.csv");

        runner.run(args);

        verify(importService).importFiles(List.of("input.csv"));
    }
}

This example assumes an ImportService with an importFiles(List<String> paths) method and the Mockito support included by the usual Spring Boot test starter. For application-level integration tests, use a Spring Boot test context and verify observable behavior. Avoid tests that depend on incidental bean ordering; explicitly declare order if order is part of the requirement.

Interview questions

  1. When does Spring Boot invoke runner beans?
    After the application context has been refreshed and before it signals that the application is ready.
  2. What is the difference between CommandLineRunner and ApplicationRunner?
    The former receives raw strings; the latter receives parsed ApplicationArguments with option and non-option argument access.
  3. How do you order multiple runners?
    Use @Order or implement Ordered, and avoid relying on bean discovery order.
  4. What happens if a runner throws an exception?
    An uncaught exception propagates as a startup failure; the application does not complete normal startup.
  5. Why should startup tasks be idempotent?
    Runners execute on every application start and on every replica, so repeating the task should not corrupt or duplicate state.
  6. When might an event listener be preferable?
    When reacting to a specific lifecycle event, such as application readiness, is more appropriate than registering a startup callback.
