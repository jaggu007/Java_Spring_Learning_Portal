What is a build system?

A Java build system automates the repeatable steps that turn source code into a runnable or deployable application. It resolves libraries, compiles code, runs tests, copies resources, and creates artifacts such as JAR or WAR files.

Spring Boot projects commonly use Apache Maven or Gradle. Spring Boot works with either; the build tool is responsible for executing the build, while Spring Boot provides conventions, dependency management, plugins, and packaging support.

By the end of this lesson, you should be able to:
  • Describe the main stages of a Java build.
  • Explain dependencies, starters, and dependency management.
  • Read a basic Maven pom.xml and Gradle build.gradle.
  • Use the project wrapper to test and package a Spring Boot application.

What happens during a build?

  1. Resolve dependencies: obtain required libraries and plugins from configured repositories and cache them locally.
  2. Compile: compile production Java sources, typically from src/main/java.
  3. Process resources: copy configuration and other resources from src/main/resources.
  4. Test: compile and run tests from src/test/java.
  5. Package: assemble compiled classes and resources into a JAR or WAR.
  6. Verify and publish: run configured checks and, when needed, publish the artifact to a repository.

A typical Java project follows this layout:

my-app/
├── src/
│   ├── main/
│   │   ├── java/          # Application source
│   │   └── resources/     # Configuration and static resources
│   └── test/
│       ├── java/          # Automated tests
│       └── resources/     # Test-only resources
├── pom.xml                # Maven build definition
└── mvnw / mvnw.cmd        # Maven Wrapper (if enabled)

Apache Maven

Maven describes a project in an XML file named pom.xml (Project Object Model). It uses a conventional directory layout and a lifecycle made up of ordered phases. Invoking a later phase also runs the earlier phases in that lifecycle.

PhasePurpose
validateCheck that the project structure and required information are valid.
compileCompile the main application source.
testRun unit tests.
packageCreate a JAR or WAR from the compiled application.
verifyRun additional checks on the packaged result.
installPlace the artifact in the local Maven repository for other local projects.
deployPublish the artifact to a configured remote repository.

Example: Spring Boot Maven project

This example uses the Spring Boot parent for managed dependency and plugin defaults. Choose a Spring Boot release compatible with your project and Java version.

<?xml version="1.0" encoding="UTF-8"?>
<project xmlns="http://maven.apache.org/POM/4.0.0"
         xmlns:xsi="http://www.w3.org/2001/XMLSchema-instance"
         xsi:schemaLocation="http://maven.apache.org/POM/4.0.0
         https://maven.apache.org/xsd/maven-4.0.0.xsd">
  <modelVersion>4.0.0</modelVersion>

  <parent>
    <groupId>org.springframework.boot</groupId>
    <artifactId>spring-boot-starter-parent</artifactId>
    <version>3.4.0</version>
    <relativePath/>
  </parent>

  <groupId>com.example</groupId>
  <artifactId>course-api</artifactId>
  <version>0.0.1-SNAPSHOT</version>
  <name>course-api</name>

  <properties>
    <java.version>17</java.version>
  </properties>

  <dependencies>
    <dependency>
      <groupId>org.springframework.boot</groupId>
      <artifactId>spring-boot-starter-web</artifactId>
    </dependency>
    <dependency>
      <groupId>org.springframework.boot</groupId>
      <artifactId>spring-boot-starter-test</artifactId>
      <scope>test</scope>
    </dependency>
  </dependencies>

  <build>
    <plugins>
      <plugin>
        <groupId>org.springframework.boot</groupId>
        <artifactId>spring-boot-maven-plugin</artifactId>
      </plugin>
    </plugins>
  </build>
</project>

spring-boot-starter-web is a starter: a convenient dependency set for common web application needs. The Spring Boot parent manages compatible versions, so the example does not specify a version on each dependency. The test starter is restricted to the test scope and is not included as a production dependency.

Gradle

Gradle defines builds using a Groovy or Kotlin DSL. A project may use build.gradle (Groovy) or build.gradle.kts (Kotlin). Gradle tasks can be composed and customized, and the Gradle Wrapper provides a consistent Gradle version for the project.

Example: Gradle with the Groovy DSL

plugins {
    id 'java'
    id 'org.springframework.boot' version '3.4.0'
    id 'io.spring.dependency-management' version '1.1.6'
}

group = 'com.example'
version = '0.0.1-SNAPSHOT'

java {
    toolchain {
        languageVersion = JavaLanguageVersion.of(17)
    }
}

dependencies {
    implementation 'org.springframework.boot:spring-boot-starter-web'
    testImplementation 'org.springframework.boot:spring-boot-starter-test'
}

tasks.named('test') {
    useJUnitPlatform()
}

The implementation configuration declares an application dependency. testImplementation makes a dependency available to test code. The Spring Boot Gradle plugin supports tasks such as bootRun and bootJar.

Maven and Gradle at a glance

AspectMavenGradle
Build definitionXML in pom.xmlGroovy or Kotlin DSL

Common commandsmvn test, mvn package./gradlew test, ./gradlew build
Wrappermvnw / mvnw.cmdgradlew / gradlew.bat

Neither tool is universally better. Follow the build tool already used by the project unless there is a clear reason to migrate.

Everyday build commands

TaskMavenGradle Wrapper
Run the application./mvnw spring-boot:run./gradlew bootRun
Run tests./mvnw test./gradlew test
Build/package./mvnw clean package./gradlew clean build
Skip tests (use sparingly)./mvnw package -DskipTests./gradlew build -x test

On Windows, use mvnw.cmd or gradlew.bat. The wrapper scripts download and invoke the project-selected build-tool version, reducing “works on my machine” differences. Prefer the wrapper over a globally installed tool for team and CI builds.

Executable Spring Boot archives

The Spring Boot Maven or Gradle plugin can package an executable JAR containing the application and its runtime dependencies. After a successful package/build, run it with Java:

java -jar target/course-api-0.0.1-SNAPSHOT.jar

Maven normally writes packaged artifacts to target/; Gradle writes them to build/libs/. A Spring Boot executable JAR can be launched with java -jar; it is different from a plain library JAR that expects dependencies on an external classpath.

Common build problems

  • Wrong Java version: check the project’s Java setting and the installed JDK. Maven and Gradle toolchains can help select a consistent compiler.
  • Dependency resolution fails: check the artifact coordinates, repository availability, network access, and any proxy configuration.
  • Conflicting dependency versions: let the Spring Boot dependency management choose compatible versions unless an override is intentional and tested.
  • Tests are not discovered: verify test naming, test framework dependencies, and test task configuration.
  • Application starts locally but not from the JAR: build the executable archive with the Spring Boot plugin and launch the generated artifact.
  • Build works only on one computer: use the project wrapper and commit its wrapper configuration and scripts.

Interview questions

  1. What does a build system do?
    It automates dependency resolution, compilation, testing, packaging, and other repeatable project tasks.
  2. What is a Spring Boot starter?
    A curated dependency descriptor that brings in a useful set of related libraries for a feature, such as web development.
  3. Why use the Maven or Gradle Wrapper?
    It runs the build with the version selected by the project, without requiring each developer or CI machine to install that version globally.
  4. What is the difference between package and install in Maven?
    package creates the artifact; install also places it in the local Maven repository.
  5. What does dependency management provide?
    It centralizes or constrains dependency versions so compatible libraries can be used consistently.
