Spring Boot Code Structure

Learn how a Spring Boot project is organized, how its application context is assembled, and where each part of your application belongs.

← Previous: Build Systems Unit 5 Home Next: Runners →

Learning outcomes

After this lesson, you should be able to explain a conventional Spring Boot directory layout, describe what the main application class does, organize code into responsibilities, and locate application configuration and tests.

Core idea: Spring Boot does not require one exact folder structure. A conventional structure makes code easier to discover, supports component scanning, and keeps application responsibilities clear.

1. Standard project layout

Maven and Gradle Spring Boot projects typically use the same source layout. The build tool controls the build; the folders organize production and test code.

course-api/
├── pom.xml                         # Maven build (or build.gradle / build.gradle.kts)
├── mvnw                            # Maven Wrapper (if enabled)
├── src/
│   ├── main/
│   │   ├── java/
│   │   │   └── com/example/course/
│   │   │       ├── CourseApplication.java
│   │   │       ├── controller/
│   │   │       ├── service/
│   │   │       ├── repository/
│   │   │       ├── model/
│   │   │       ├── dto/
│   │   │       ├── exception/
│   │   │       └── config/
│   │   └── resources/
│   │       ├── application.properties
│   │       ├── static/             # Static web assets, when needed
│   │       └── templates/          # Server-rendered templates, when needed
│   └── test/
│       ├── java/
│       │   └── com/example/course/
│       └── resources/
│           └── application-test.properties
  • src/main/java holds Java source compiled into the application.
  • src/main/resources holds files copied to the runtime classpath, including configuration and application resources.
  • src/test/java holds automated tests; test code is not part of the production artifact.
  • src/test/resources contains files used only by tests.
  • static and templates are conventional resource folders for static files and server-side view templates; APIs do not need them unless those features are used.

2. The application entry point

A Spring Boot application normally has one main class with a Java main method. SpringApplication.run bootstraps Spring, creates the application context, loads configured beans, and starts the embedded web server when a web application is on the classpath.

package com.example.course;

import org.springframework.boot.SpringApplication;
import org.springframework.boot.autoconfigure.SpringBootApplication;

@SpringBootApplication
public class CourseApplication {
    public static void main(String[] args) {
        SpringApplication.run(CourseApplication.class, args);
    }
}

@SpringBootApplication is a convenience annotation that combines:

  • @SpringBootConfiguration (a specialized @Configuration): marks the class as a source of bean definitions.
  • @EnableAutoConfiguration: asks Spring Boot to configure beans based on the classpath, existing beans, and application properties.
  • @ComponentScan: searches for Spring components in the application package and its subpackages by default.
Package placement matters: put the application class in a root package such as com.example.course, above controller, service, and other application packages. If it is nested too deeply, component scanning may not discover sibling packages.

3. Organizing by responsibility

A common layered design separates the HTTP boundary, business logic, and data access. This is a useful convention, not a rule imposed by Spring Boot.

Package / layerTypical responsibilityCommon Spring types
controllerAccept HTTP requests, validate input, select response status and representation.@Controller, @RestController
serviceImplement use cases and coordinate business operations.@Service
repositoryLoad and persist domain data; isolate database access.@Repository, Spring Data repository interfaces
model / entityRepresent domain concepts; persistence entities map to database tables when using an ORM.Java classes, optionally @Entity
dtoRepresent input and output data shapes at API boundaries.Records or ordinary Java classes
configDeclare explicit infrastructure or integration beans and configuration.@Configuration, @Bean
exceptionDefine application exceptions and central error mapping.@ControllerAdvice, @ExceptionHandler

A typical request path is controller → service → repository. The controller should handle transport concerns, the service should own the use case, and the repository should handle persistence. Avoid making a controller perform database work directly or returning persistence entities automatically as public API contracts.

4. A small dependency-injected example

Each class lives in the package that matches its directory. Constructor injection makes required dependencies explicit and keeps the service straightforward to test.

service/GreetingService.java

package com.example.course.service;

import org.springframework.stereotype.Service;

@Service
public class GreetingService {
    public String greetingFor(String name) {
        return "Hello, " + name + "!";
    }
}

controller/GreetingController.java

package com.example.course.controller;

import com.example.course.service.GreetingService;
import org.springframework.web.bind.annotation.GetMapping;
import org.springframework.web.bind.annotation.RequestParam;
import org.springframework.web.bind.annotation.RestController;

@RestController
public class GreetingController {
    private final GreetingService greetingService;

    public GreetingController(GreetingService greetingService) {
        this.greetingService = greetingService;
    }

    @GetMapping("/greeting")
    public String greeting(
            @RequestParam(defaultValue = "World") String name) {
        return greetingService.greetingFor(name);
    }
}

During startup, component scanning discovers both annotated classes. Spring creates the GreetingService bean and supplies it to the controller constructor. With one constructor, Spring can use it for injection without an explicit @Autowired.

5. External configuration

Place default application settings in src/main/resources/application.properties or application.yml. Externalized configuration lets deployments change ports, logging, and other settings without changing Java source.

application.properties

spring.application.name=course-api
server.port=8080
logging.level.com.example.course=INFO

For related settings, bind configuration to a typed class using @ConfigurationProperties. Register the properties class by adding @ConfigurationPropertiesScan to the application class (or use @EnableConfigurationProperties(CourseProperties.class)):

import org.springframework.boot.context.properties.ConfigurationPropertiesScan;

@SpringBootApplication
@ConfigurationPropertiesScan
public class CourseApplication {
    // main method
}
package com.example.course.config;

import org.springframework.boot.context.properties.ConfigurationProperties;

@ConfigurationProperties(prefix = "course")
public record CourseProperties(String welcomeMessage) { }
# application.properties
course.welcome-message=Welcome to the course

Spring Boot supports multiple property sources. Command-line arguments, environment variables, and external configuration can override packaged defaults according to Spring Boot’s property-source precedence. Do not commit credentials or other secrets in source-controlled configuration; inject them through an appropriate secret store or deployment environment.

6. Profiles and environment-specific settings

Profiles allow a set of beans or configuration values to be active only in a particular environment. For example, local development and tests can use different database settings.

# src/main/resources/application.properties
spring.profiles.default=dev

# src/main/resources/application-dev.properties
server.port=8080

# src/test/resources/application-test.properties
server.port=0

Activate a profile with --spring.profiles.active=test or the corresponding environment variable. Use profiles for intentional environment differences; avoid treating them as a substitute for secure secret management.

7. Testing the structure

Tests should mirror production packages under src/test/java. Unit tests can instantiate a class directly; Spring integration tests load an application context and verify framework wiring.

Service unit test without starting Spring

package com.example.course.service;

import static org.junit.jupiter.api.Assertions.assertEquals;

import org.junit.jupiter.api.Test;

class GreetingServiceTest {
    private final GreetingService service = new GreetingService();

    @Test
    void createsGreetingForName() {
        assertEquals("Hello, Ada!", service.greetingFor("Ada"));
    }
}

Application context smoke test

package com.example.course;

import org.junit.jupiter.api.Test;
import org.springframework.boot.test.context.SpringBootTest;

@SpringBootTest
class CourseApplicationTests {
    @Test
    void contextLoads() {
    }
}

@SpringBootTest starts the Spring application context for the test. It is useful for integration coverage, but it is slower than a focused unit test. Prefer a narrow test when only one class’s logic needs verification.

8. Common structure and startup problems

  • “No qualifying bean”: check that the implementation is registered as a bean, its package is within component scan, and the required dependency is on the classpath.
  • Application starts but controller is not found: move the main application class to a suitable root package or configure scanning deliberately.
  • Configuration value is missing: confirm the file is in src/main/resources, the property name is correct, and the intended profile is active.
  • Multiple beans of the same type: resolve ambiguity with a clear design, a qualifier, or a primary bean rather than relying on accidental scan order.
  • Fat controller or service: split transport handling, use-case logic, and persistence responsibilities into appropriate components.
  • Secrets in source control: remove credentials from committed configuration and load them from an environment-specific secure source.
  • Unexpected component discovery: component scan is package-based, not directory-name-based; Java package declarations and folder paths should agree.

Interview questions

  1. What does @SpringBootApplication combine?
    @SpringBootConfiguration, @EnableAutoConfiguration, and @ComponentScan.
  2. Why should the main application class usually be in a root package?
    Its default component scan covers its package and descendants, so placing it above application components helps Spring discover them.
  3. What is the difference between src/main/resources and src/test/resources?
    The first supplies runtime application resources; the second supplies test-only resources.
  4. Why use constructor injection?
    It makes required dependencies explicit, supports immutable fields, and allows simple tests without starting Spring.
  5. What is the role of a service layer?
    It coordinates application use cases and business logic independently from HTTP request handling and data access.
  6. When is @SpringBootTest appropriate?
    When a test needs the real application context or integration between Spring-managed components, rather than only testing isolated class logic.
