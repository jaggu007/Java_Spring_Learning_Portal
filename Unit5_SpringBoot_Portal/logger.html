Logging in Spring Boot

Use structured, appropriately leveled logs to understand application behavior, diagnose failures, and operate services safely.

← Previous: Runners Unit 5 Home Next: RESTful Web Services →

Learning outcomes

After this lesson, you should be able to create a logger with SLF4J, choose useful log levels, configure logging in Spring Boot, record exceptions correctly, and avoid exposing sensitive data.

Default stack: Spring Boot starters typically configure SLF4J as the logging API and Logback as the default logging implementation. Application classes should use the SLF4J API rather than depending directly on Logback-specific classes.

1. Why logging matters

Logs are timestamped records of significant application events. They help developers and operators answer what happened, when it happened, and which part of the application was involved. Useful logs provide context while avoiding excessive noise.

Logging is different from:

  • Printing to the console: System.out.println has no built-in level, structured formatting, or standard filtering.
  • Metrics: metrics summarize numeric behavior over time, such as request rates and latency.
  • Distributed traces: traces connect work across services and components. Logs can complement traces through shared identifiers.

2. Log levels

A level expresses the importance of a log event. A configured threshold filters lower-severity events. The common severity order, from least to most severe, is:

LevelTypical useExample
TRACEVery detailed diagnostic events, often useful only temporarily.Fine-grained steps inside a complex algorithm.
DEBUGDeveloper diagnostics that are normally disabled in production.Non-sensitive values used to explain a decision.
INFOImportant normal milestones in application operation.Service started or scheduled import completed.
WARNAn unexpected or degraded condition that the application can handle.Optional external feature unavailable; fallback used.
ERRORAn operation failed and needs attention.Request processing or a background operation failed.

Choose the level based on operational meaning, not merely on which method is convenient. Avoid logging every method entry at INFO; high-volume logs make important events difficult to find and increase storage cost.

3. Create and use an SLF4J logger

Declare a logger for the class and use parameterized messages. The {} placeholders defer string formatting until the log event is enabled.

package com.example.course.service;

import org.slf4j.Logger;
import org.slf4j.LoggerFactory;
import org.springframework.stereotype.Service;

@Service
public class EnrollmentService {
    private static final Logger log =
            LoggerFactory.getLogger(EnrollmentService.class);

    public void enroll(String studentId, String courseCode) {
        log.info("Starting enrollment for course {}", courseCode);

        try {
            // Perform the enrollment operation.
            log.debug("Enrollment operation completed for course {}",
                    courseCode);
        } catch (RuntimeException exception) {
            log.error("Enrollment failed for course {}", courseCode,
                    exception);
            throw exception;
        }
    }
}
  • Use parameterized messages such as log.debug("Loaded {} records", count).
  • Pass the exception as the final argument when a stack trace is useful: log.error("Operation failed", exception).
  • Do not concatenate strings unnecessarily, especially in frequently called debug statements.
  • Log stable identifiers when helpful, but ensure they are safe to record and comply with privacy requirements.

4. Configure logging levels

Spring Boot lets you set the root logging level and fine-tune individual packages. Put configuration in src/main/resources/application.properties or YAML.

# application.properties
logging.level.root=INFO
logging.level.com.example.course=DEBUG
logging.level.org.springframework.web=WARN

Equivalent YAML:

logging:
  level:
    root: INFO
    com.example.course: DEBUG
    org.springframework.web: WARN

Setting a package level to DEBUG does not mean every library becomes verbose. Package-level configuration helps target the output. Use environment-specific configuration to keep production logging useful and controlled.

5. Log output and configuration files

Spring Boot’s default console output is suitable for local development and container environments that collect standard output. To write to a file, configure one of the supported file properties:

logging.file.name=logs/course-api.log
logging.logback.rollingpolicy.max-file-size=10MB
logging.logback.rollingpolicy.max-history=14

For detailed appenders, layouts, or rolling policies, provide a Logback configuration such as logback-spring.xml. The -spring variant supports Spring Boot extensions, including profile-aware configuration. Avoid adding a separate logging implementation alongside the default without a deliberate migration; multiple bindings can cause conflicts.

6. Logging exceptions correctly

At an error boundary, log an exception with its throwable so the logger records the stack trace. Avoid logging the same exception at every layer: repeated stack traces create noise and obscure the original failure.

try {
    paymentGateway.charge(request);
} catch (PaymentException exception) {
    log.error("Payment charge failed for order {}", orderId, exception);
    throw exception;
}

When an exception is translated into an HTTP response, centralize error mapping where appropriate (for example with @ControllerAdvice). Choose a consistent layer to record the failure, include a safe correlation identifier, and return an appropriate response without exposing internal stack traces to clients.

Avoid: log.error("Failed: " + exception.getMessage()) as the only diagnostic. It may omit the stack trace and important cause chain. Also avoid catching an exception only to log it and continue as if the operation succeeded.

7. Correlation IDs and request context

In a distributed application, a request may cross multiple services. A correlation or trace identifier helps connect related events. Observability libraries can propagate trace context and add identifiers to logs automatically. If configuring Logback’s mapped diagnostic context (MDC) manually, always clear request-specific values when work finishes, especially when using thread pools, to prevent context leaking into another request.

import org.slf4j.MDC;

try {
    MDC.put("requestId", requestId);
    log.info("Processing request");
    // Handle request work.
} finally {
    MDC.remove("requestId");
}

In servlet applications, request filters or framework instrumentation are usually better places to set and clear request context than individual controller methods. Do not invent a separate trace identifier if a tracing system already provides one.

8. Security, privacy, and production practices

  • Never log secrets: passwords, access tokens, API keys, session cookies, private keys, and full authorization headers do not belong in logs.
  • Minimize personal data: avoid logging full request bodies or sensitive identifiers. Redact or pseudonymize values when diagnostic context is necessary.
  • Sanitize untrusted input: attacker-controlled newlines and delimiters can forge or confuse log entries. Use structured logging and validate or encode user-supplied values.
  • Keep messages actionable: include operation names and safe identifiers, not ambiguous messages such as “something went wrong.”
  • Control volume and retention: use suitable production levels, rotation or platform log retention, and avoid high-cardinality or per-request debug output by default.
  • Keep stack traces server-side: API responses should not expose internal implementation details, credentials, or stack traces.

9. Testing and troubleshooting

Most business logic should be tested through its observable results rather than by asserting exact log message wording. When a log event is itself part of a requirement, use a test appender or a logging test utility appropriate to the chosen backend.

SymptomCheck
No debug messages appearSet the relevant package to DEBUG; a higher threshold filters them.
Duplicate log entriesCheck for duplicate logging dependencies, multiple appenders, or additivity in custom Logback configuration.
Stack trace is missingPass the throwable as an argument to the logging call rather than only logging its message.
File logs do not appearCheck the configured file property, process working directory, filesystem permissions, and container logging strategy.
Wrong request ID appearsEnsure MDC values are removed in a finally block or use framework instrumentation that handles context propagation.

Interview questions

  1. What is SLF4J?
    A logging facade that provides a common API, allowing application code to use a logging implementation such as Logback behind it.
  2. What is the difference between WARN and ERROR?
    WARN indicates an unexpected or degraded condition that may be handled; ERROR indicates an operation failed and likely needs attention.
  3. Why use parameterized logging?
    It avoids unnecessary message formatting when the level is disabled and keeps messages clear.
  4. How should a throwable be logged?
    Pass it to the logging method as the throwable argument so the backend can include the stack trace.
  5. Why should exceptions not be logged at every layer?
    Repeated logging duplicates stack traces and makes it harder to find the point where a failure was handled.
  6. What is MDC used for?
    It associates contextual values, such as a request or trace identifier, with log events; values must be safely cleared or propagated across threads.
