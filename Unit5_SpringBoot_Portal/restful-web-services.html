Building RESTful Web Services

Design resource-oriented HTTP APIs and understand how Spring Boot maps requests, validates data, and returns meaningful responses.

← Previous: Logging Unit 5 Home Next: REST Controller →

Learning outcomes

After this lesson, you should be able to explain REST and HTTP resource modeling, select HTTP methods and status codes, design predictable endpoints, and describe how Spring Boot handles JSON requests and responses.

REST is an architectural style, not a Spring annotation. Spring MVC provides the HTTP infrastructure; application design determines whether an API uses resources, methods, representations, and status codes coherently.

1. REST and resources

Representational State Transfer (REST) is an architectural style for distributed systems. A RESTful API exposes resources identified by URIs. Clients use HTTP methods to act on those resources, and exchange representations—commonly JSON—rather than directly manipulating server-side objects.

For a course API, possible resources include:

  • /api/courses — the collection of courses.
  • /api/courses/42 — the course identified by 42.
  • /api/courses/42/students — students associated with that course, when the relationship is part of the API design.

Resource names are generally nouns. HTTP methods communicate the action. Prefer GET /api/courses/42 over action-oriented paths such as /api/getCourse?id=42.

Common REST constraints

  • Client-server: separates the user interface from data and service concerns.
  • Stateless: each request contains the context needed to process it; the server does not rely on hidden client session state between requests.
  • Cacheable: responses indicate whether they may be cached and for how long where appropriate.
  • Uniform interface: resources, representations, and standard HTTP semantics are used consistently.
  • Layered system: clients need not know whether they communicate through proxies, gateways, or other intermediaries.
  • Code on demand (optional): a server may provide executable code to clients, though this is uncommon for typical JSON APIs.

2. HTTP methods and their semantics

MethodTypical purposeSafe?Idempotent?
GETRetrieve a resource or collection.YesYes
POSTCreate a subordinate resource or submit a processing request.NoNot generally

PATCHApply a partial modification to a resource.NoNot inherently; depends on the patch operation

Safe means the request is defined as read-only. Idempotent means repeating the same request has the same intended effect as making it once; the response itself need not be identical. A DELETE can return a different status on a repeated request while remaining idempotent in effect.

3. HTTP status codes

Use status codes to communicate the outcome at the HTTP layer. The response body can provide additional details, but clients should not have to infer success or failure from a message string alone.

4. Designing predictable endpoints

Use consistent collection and item paths. Keep filters and sorting in query parameters; use path segments to identify a specific resource.

OperationRequestTypical response
List coursesGET /api/courses?page=0&size=20200 OK with a page of course representations.
Read courseGET /api/courses/42200 OK or 404 Not Found.
Create coursePOST /api/courses with JSON201 Created, ideally with a Location header.
Replace coursePUT /api/courses/42 with a complete representation200 OK with representation or 204 No Content.
Partially updatePATCH /api/courses/42 with a documented patch format200 OK or 204 No Content.
Delete courseDELETE /api/courses/42204 No Content or a documented alternative.
  • Use plural collection names consistently, such as /courses.
  • Use query parameters for filtering, pagination, and sorting, such as ?status=active&page=0&size=20.
  • Set sensible maximum page sizes and validate client-supplied values.
  • Document whether an endpoint returns a complete resource, a summary, or a collection envelope.
  • Use a consistent API versioning strategy if compatibility requirements call for one; versioning can be done in paths or through media types, and should be deliberate.
  • Use cache headers and conditional requests where the resource and client behavior benefit from caching.

5. Representations, headers, and content negotiation

HTTP headers describe the request and response. The body carries the representation.

  • Content-Type describes the request or response body format, commonly application/json.
  • Accept tells the server which response media types the client can handle.
  • Location identifies a newly created resource, commonly returned with 201 Created.
  • Cache-Control, ETag, and Last-Modified can support caching and conditional requests.

Spring Boot web applications typically use Jackson to serialize Java objects to JSON and deserialize JSON request bodies. Keep the public representation intentional: API DTOs allow internal persistence models to change without silently changing the API contract.

{
  "id": 42,
  "code": "CS336B",
  "title": "OOPS with Java"
}

6. A REST endpoint in Spring Boot

The following example shows a small HTTP boundary. @RestController marks the class as a controller whose return values are written to the response body. @GetMapping maps an HTTP GET request to a handler method.

package com.example.course.controller;

import java.util.List;

import org.springframework.http.HttpStatus;
import org.springframework.web.bind.annotation.GetMapping;
import org.springframework.web.bind.annotation.PathVariable;
import org.springframework.web.bind.annotation.PostMapping;
import org.springframework.web.bind.annotation.RequestBody;
import org.springframework.web.bind.annotation.RequestMapping;
import org.springframework.web.bind.annotation.ResponseStatus;
import org.springframework.web.bind.annotation.RestController;

@RestController
@RequestMapping("/api/courses")
public class CourseController {
    private final CourseService courseService;

    public CourseController(CourseService courseService) {
        this.courseService = courseService;
    }

    @GetMapping
    public List<CourseResponse> listCourses() {
        return courseService.findAll();
    }

    @GetMapping("/{id}")
    public CourseResponse getCourse(@PathVariable long id) {
        return courseService.findById(id);
    }

    @PostMapping
    @ResponseStatus(HttpStatus.CREATED)
    public CourseResponse createCourse(
            @RequestBody CreateCourseRequest request) {
        return courseService.create(request);
    }
}

CourseService, CourseResponse, and CreateCourseRequest represent application-layer types supplied by the application. In a production API, requests should be validated and persistence should normally be handled behind the service boundary.

7. DTOs and request validation

A data transfer object (DTO) defines the data accepted or returned by an endpoint. Separate request and response DTOs prevent clients from setting server-owned fields such as database IDs or administrative flags.

package com.example.course.dto;

import jakarta.validation.constraints.NotBlank;
import jakarta.validation.constraints.Size;

public record CreateCourseRequest(
        @NotBlank
        @Size(max = 20)
        String code,

        @NotBlank
        @Size(max = 120)
        String title
) {}

Trigger Bean Validation by placing @Valid on the request body parameter. Include the validation starter (commonly spring-boot-starter-validation) in the build when it is not already present.

import jakarta.validation.Valid;

@PostMapping
@ResponseStatus(HttpStatus.CREATED)
public CourseResponse createCourse(
        @Valid @RequestBody CreateCourseRequest request) {
    return courseService.create(request);
}

Validation should protect both the API boundary and domain invariants. A syntactically valid request may still fail a business rule—for example, attempting to create a course with a code that already exists.

8. Consistent error responses

Return a stable, documented error shape and an appropriate HTTP status. Do not send Java stack traces, SQL details, or internal exception messages to clients. Spring Framework supports the standard ProblemDetail response model for HTTP API errors.

{
  "type": "about:blank",
  "title": "Not Found",
  "status": 404,
  "detail": "Course 42 was not found",
  "instance": "/api/courses/42"
}

Centralize exception-to-response mapping with @RestControllerAdvice and @ExceptionHandler when multiple controllers need the same policy. Use distinct handling for validation errors, missing resources, conflicts, and unexpected failures. Log unexpected server failures with a correlation ID, while returning only safe client-facing details.

9. Calling the API

Example request to retrieve a course:

curl -i \
  -H "Accept: application/json" \
  http://localhost:8080/api/courses/42

Example JSON creation request:

curl -i \
  -X POST \
  -H "Content-Type: application/json" \
  -H "Accept: application/json" \
  -d '{"code":"CS336B","title":"OOPS with Java"}' \
  http://localhost:8080/api/courses

Inspect the status line and headers as well as the response body. A successful POST should report creation using the agreed status and, where available, a resource location.

10. API security and reliability

  • Authenticate and authorize: use a security mechanism appropriate to the application, and check authorization for each resource operation.
  • Use HTTPS: protect credentials and data in transit.
  • Validate input: enforce size, format, range, and business constraints; do not trust client-provided IDs or roles.
  • Prevent excessive resource use: cap page sizes and request sizes, and apply appropriate rate limits.
  • Handle concurrent updates: consider optimistic locking with entity versions or conditional requests such as ETag and If-Match.
  • Protect against duplicate submissions: where clients may retry creation after a timeout, consider an idempotency key and define its semantics.
  • Configure CORS narrowly: allow only intended browser origins, methods, and headers; CORS is not authentication.
  • Document the contract: describe endpoints, schemas, statuses, and authentication so clients can integrate safely.

Interview questions

  1. What is a resource in REST?
    A conceptual entity identified by a URI and represented through data exchanged between client and server.
  2. What is the difference between safe and idempotent HTTP methods?
    Safe methods are intended to read without changing server state; idempotent methods have the same intended effect when repeated.
  3. When should a create endpoint return 201 Created?
    When the request successfully creates a resource; the response can identify it with a Location header.
  4. Why use request and response DTOs?
    They define and validate the API contract without exposing persistence details or allowing clients to set server-controlled fields.
  5. What is content negotiation?
    The client and server use headers such as Accept and Content-Type to agree on representation formats.
  6. Why is 401 different from 403?
    401 means valid authentication is missing or absent; 403 means the authenticated client is not permitted to perform the operation.
