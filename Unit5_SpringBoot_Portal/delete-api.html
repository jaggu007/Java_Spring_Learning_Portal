Building a DELETE API

A step-by-step Spring Boot tutorial for safely deleting a resource by ID.

← Previous: PUT API Unit 5 Home Next: Build Web Applications →

What you will build

We will implement DELETE /api/courses/{id} using a Spring MVC controller, service, and Spring Data repository. The tutorial uses an update-only deletion policy: the first successful deletion returns 204 No Content; an unknown ID returns 404 Not Found.

DELETE is idempotent in intended effect. Repeating a delete does not further change the resource state. The API may still return 404 on a repeated request after the resource is gone; idempotency does not require identical response codes.

How the request flows

Step 1: Add the required project dependencies

In Spring Initializr, select Spring Web and Spring Data JPA, then select the driver for the database used by your project. For Maven, the main dependencies look like this (the database driver is database-specific):

<dependency>
    <groupId>org.springframework.boot</groupId>
    <artifactId>spring-boot-starter-web</artifactId>
</dependency>
<dependency>
    <groupId>org.springframework.boot</groupId>
    <artifactId>spring-boot-starter-data-jpa</artifactId>
</dependency>

A typical package layout:

src/main/java/com/example/course/
├── controller/CourseController.java
├── entity/Course.java
├── exception/CourseNotFoundException.java
├── repository/CourseRepository.java
└── service/CourseService.java

Step 2: Create the entity

This JPA entity represents a row in the courses table. The example uses a generated ID and a no-argument constructor required by JPA.

package com.example.course.entity;

import jakarta.persistence.Entity;
import jakarta.persistence.GeneratedValue;
import jakarta.persistence.GenerationType;
import jakarta.persistence.Id;
import jakarta.persistence.Table;

@Entity
@Table(name = "courses")
public class Course {
    @Id
    @GeneratedValue(strategy = GenerationType.IDENTITY)
    private Long id;

    private String code;
    private String title;

    protected Course() {
    }

    public Long getId() {
        return id;
    }
}

Real applications should also define database constraints, relationships, and schema migrations according to their domain. The DELETE API only needs the ID and repository for this example.

Step 3: Define a repository

Spring Data JPA provides findById and delete from JpaRepository, so no custom SQL is needed for this basic operation.

package com.example.course.repository;

import com.example.course.entity.Course;
import org.springframework.data.jpa.repository.JpaRepository;

public interface CourseRepository extends JpaRepository<Course, Long> {
}

Spring creates the repository implementation at runtime. The ID type in JpaRepository<Course, Long> should match the entity’s @Id type.

Step 4: Define a not-found exception

Represent the expected “resource does not exist” condition explicitly so it can be translated to HTTP 404.

package com.example.course.exception;

public class CourseNotFoundException extends RuntimeException {
    public CourseNotFoundException(long id) {
        super("Course " + id + " was not found");
    }
}

Step 5: Implement deletion in the service

The service verifies that the course exists and deletes it within a transaction. The existence check allows the API to distinguish a missing resource from a successful deletion.

package com.example.course.service;

import com.example.course.entity.Course;
import com.example.course.exception.CourseNotFoundException;
import com.example.course.repository.CourseRepository;
import org.springframework.stereotype.Service;
import org.springframework.transaction.annotation.Transactional;

@Service
public class CourseService {
    private final CourseRepository repository;

    public CourseService(CourseRepository repository) {
        this.repository = repository;
    }

    @Transactional
    public void delete(long id) {
        Course course = repository.findById(id)
                .orElseThrow(() -> new CourseNotFoundException(id));
        repository.delete(course);
    }
}

In concurrent systems, the resource could change between lookup and delete. The database operation and transaction remain authoritative. If concurrent deletion is common, decide whether a second delete should be treated as not found or as a successful no-op and implement that policy consistently.

Step 6: Expose the DELETE endpoint

Use @DeleteMapping and a @PathVariable to identify the resource. Return 204 No Content after successful deletion; a 204 response must not include a response body.

package com.example.course.controller;

import com.example.course.service.CourseService;
import org.springframework.http.ResponseEntity;
import org.springframework.web.bind.annotation.DeleteMapping;
import org.springframework.web.bind.annotation.PathVariable;
import org.springframework.web.bind.annotation.RequestMapping;
import org.springframework.web.bind.annotation.RestController;

@RestController
@RequestMapping("/api/courses")
public class CourseController {
    private final CourseService courseService;

    public CourseController(CourseService courseService) {
        this.courseService = courseService;
    }

    @DeleteMapping("/{id}")
    public ResponseEntity<Void> deleteCourse(
            @PathVariable long id) {
        courseService.delete(id);
        return ResponseEntity.noContent().build();
    }
}

The composed route is DELETE /api/courses/{id}. Keep the controller thin: it delegates the operation and communicates the HTTP response.

Step 7: Map missing resources to HTTP 404

Use a shared @RestControllerAdvice to translate the service exception into a consistent client response. This avoids returning internal exception details.

import com.example.course.exception.CourseNotFoundException;
import org.springframework.http.HttpStatus;
import org.springframework.http.ProblemDetail;
import org.springframework.web.bind.annotation.ExceptionHandler;
import org.springframework.web.bind.annotation.RestControllerAdvice;

@RestControllerAdvice
public class ApiExceptionHandler {
    @ExceptionHandler(CourseNotFoundException.class)
    ProblemDetail handleCourseNotFound(
            CourseNotFoundException exception) {
        ProblemDetail problem =
                ProblemDetail.forStatus(HttpStatus.NOT_FOUND);
        problem.setTitle("Course not found");
        problem.setDetail("The requested course does not exist.");
        return problem;
    }
}

ProblemDetail is available in modern Spring Framework versions. If using an older version, return your API’s documented error DTO instead.

Step 8: Run and call the API

Start your application with its configured database available, then call the endpoint with a course ID that exists:

./mvnw spring-boot:run

curl -i -X DELETE http://localhost:8080/api/courses/42

Expected success response:

HTTP/1.1 204

(no response body)

For an unknown ID, the update-only sample returns 404 Not Found. On Windows, use mvnw.cmd spring-boot:run.

Step 9: Test success and not-found cases

Test both the HTTP contract and service behavior. A controller test can mock the service and verify the status; service tests should check repository interactions and missing-resource behavior.

import static org.mockito.Mockito.doThrow;
import static org.springframework.test.web.servlet.request.MockMvcRequestBuilders.delete;
import static org.springframework.test.web.servlet.result.MockMvcResultMatchers.status;

import com.example.course.exception.CourseNotFoundException;
import com.example.course.service.CourseService;
import org.junit.jupiter.api.Test;
import org.springframework.beans.factory.annotation.Autowired;
import org.springframework.boot.test.autoconfigure.web.servlet.WebMvcTest;
import org.springframework.test.context.bean.override.mockito.MockitoBean;
import org.springframework.test.web.servlet.MockMvc;

@WebMvcTest(CourseController.class)
class CourseControllerTest {
    @Autowired
    MockMvc mockMvc;

    @MockitoBean
    CourseService courseService;

    @Test
    void deletesExistingCourse() throws Exception {
        mockMvc.perform(delete("/api/courses/42"))
                .andExpect(status().isNoContent());
    }

    @Test
    void returnsNotFoundWhenCourseDoesNotExist() throws Exception {
        doThrow(new CourseNotFoundException(999L))
                .when(courseService).delete(999L);

        mockMvc.perform(delete("/api/courses/999"))
                .andExpect(status().isNotFound());
    }
}

Also test authorization failures, invalid identifier conversion, database constraints, and any soft-delete policy. Keep assertions focused on your API’s documented responses rather than internal exception text.

@MockitoBean is available in recent Spring Framework versions. For older project versions, use the test-context mock annotation supported by that version.

Deletion policy choices

PolicyBehaviorConsiderations
Hard deleteRemove the row from the database.Check foreign-key references, audit requirements, and retention obligations.
Soft deleteMark a resource inactive/deleted instead of physically removing it.All reads must consistently exclude deleted records; define restore and retention behavior.
Idempotent no-op for missing IDRepeated deletion returns success even if already absent.Can simplify retries, but may hide invalid IDs or require careful authorization.
Not-found for missing IDReturn 404 when no current resource exists.Clear resource-existence feedback; repeated delete can return 404 while remaining idempotent in effect.

Choose the policy based on domain, audit, privacy, and client requirements. If using a database foreign key, handle dependent records intentionally rather than bypassing referential integrity.

Security and reliability checklist

  • Authorize the specific resource: authentication alone is not permission to delete every record.
  • Protect against IDOR: scope lookups to the caller’s tenant or ownership context where applicable.
  • Consider CSRF: browser applications using cookie-based authentication need appropriate CSRF protection for state-changing requests.
  • Audit destructive actions: record who deleted what and when, without logging secrets or unnecessary personal data.
  • Review relationships: decide how dependent records, foreign keys, and storage objects are handled.
  • Use HTTPS: protect credentials and requests in transit.
  • Confirm intent for high-impact actions: use application-level confirmation or approval where the domain requires it; do not rely on obscurity.

Interview questions

  1. Which HTTP status is commonly returned when deletion succeeds without a body?
    204 No Content.
  2. Is DELETE idempotent?
    Yes in intended effect: repeating it does not further change the resource state, though the response code may differ.
  3. Should a repeated delete return 204 or 404?
    Either can be chosen as an API policy; document and apply it consistently.
  4. Why check existence before deletion?
    To implement an update-only contract that reports a missing resource as 404.
  5. What is a soft delete?
    Marking a record as deleted or inactive while retaining it for audit, recovery, or retention purposes.
  6. Why is authorization especially important for DELETE?
    It is destructive; the caller must be allowed to delete the specific resource, not merely be authenticated.
