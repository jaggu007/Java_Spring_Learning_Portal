Handling Request Bodies

Convert incoming HTTP representations into Java objects, validate them, and process client input safely.

← Previous: Request Mapping Unit 5 Home Next: Path Variable →

Learning outcomes

After this lesson, you should be able to bind a JSON request body with @RequestBody, explain how Spring message converters work, validate request DTOs, return meaningful errors, and protect the API from unsafe or oversized input.

Important distinction: @RequestBody reads and converts the HTTP body. Query parameters and path variables are bound separately with @RequestParam and @PathVariable.

1. How a JSON request body is processed

Spring MVC uses an HttpMessageConverter selected from the request’s media type and target Java type. In a typical Spring Boot web application, Jackson provides JSON conversion. The controller is invoked only after the request body has been read and converted successfully.

2. Bind a request body with @RequestBody

Place @RequestBody on a controller method parameter. Spring reads the body and asks a message converter to deserialize it into that parameter type. The body is required by default; if it is missing, Spring reports a client error rather than invoking the method with a meaningful object.

@PostMapping(
    path = "/api/courses",
    consumes = MediaType.APPLICATION_JSON_VALUE,
    produces = MediaType.APPLICATION_JSON_VALUE
)
public CourseResponse create(
        @RequestBody CreateCourseRequest request) {
    return courseService.create(request);
}

Clients should send an appropriate Content-Type header, typically application/json. The Accept header describes acceptable response media types; it is not the request-body format.

POST /api/courses HTTP/1.1
Content-Type: application/json
Accept: application/json

{
  "code": "CS336B",
  "title": "OOPS with Java",
  "credits": 4
}

3. Use request DTOs, not persistence entities

A request DTO defines exactly what the client may submit. It decouples the API contract from database entities and prevents clients from setting server-controlled fields such as IDs, ownership, internal flags, or audit timestamps.

package com.example.course.dto;

import jakarta.validation.constraints.Max;
import jakarta.validation.constraints.Min;
import jakarta.validation.constraints.NotBlank;
import jakarta.validation.constraints.Size;

public record CreateCourseRequest(
        @NotBlank
        @Size(max = 20)
        String code,

        @NotBlank
        @Size(max = 120)
        String title,

        @Min(1)
        @Max(6)
        int credits
) {}

Records are convenient immutable DTOs when the project’s Java version supports them. Ordinary classes with constructors, accessors, or setters can also be used. Keep response DTOs separate when the response shape differs from the accepted input.

4. Validate the body

Annotate DTO fields or record components with Jakarta Bean Validation constraints, then add @Valid to the @RequestBody parameter. Include the validation starter (commonly spring-boot-starter-validation) if validation is not already on the classpath.

import jakarta.validation.Valid;

@PostMapping("/api/courses")
public ResponseEntity<CourseResponse> create(
        @Valid @RequestBody CreateCourseRequest request) {
    CourseResponse created = courseService.create(request);
    return ResponseEntity
            .created(URI.create("/api/courses/" + created.id()))
            .body(created);
}

For nested DTOs, put @Valid on the nested property as well as constraints on the nested type:

public record InstructorRequest(
        @NotBlank String name,
        @Email String email
) {}

public record CreateCourseRequest(
        @NotBlank String code,
        @NotBlank String title,
        @Valid InstructorRequest instructor
) {}

Bean validation checks the input shape and declared constraints. Business rules—such as uniqueness, authorization, or whether a course can be changed after enrollment—must still be checked in the application/domain layer.

5. Validation and error response flow

For a validated request object, Spring MVC commonly raises MethodArgumentNotValidException when constraints fail. Malformed JSON or failed type conversion typically raises HttpMessageNotReadableException. Exact handling can vary with framework version and method-validation configuration.

A shared @RestControllerAdvice can turn these failures into a stable response format, such as Spring’s ProblemDetail. Include safe field-level messages for clients, but do not disclose stack traces, parser internals, or sensitive submitted values.

6. Example exception handling

import org.springframework.http.HttpStatus;
import org.springframework.http.ProblemDetail;
      import org.springframework.http.converter.HttpMessageNotReadableException;
      import org.springframework.web.bind.MethodArgumentNotValidException;
import org.springframework.web.bind.annotation.ExceptionHandler;
import org.springframework.web.bind.annotation.RestControllerAdvice;

@RestControllerAdvice
public class RequestErrorHandler {
    @ExceptionHandler(MethodArgumentNotValidException.class)
    ProblemDetail handleValidation(
            MethodArgumentNotValidException exception) {
        ProblemDetail problem =
                ProblemDetail.forStatus(HttpStatus.BAD_REQUEST);
        problem.setTitle("Request validation failed");
        problem.setDetail("One or more fields are invalid.");
        return problem;
    }

    @ExceptionHandler(HttpMessageNotReadableException.class)
    ProblemDetail handleUnreadableBody(
            HttpMessageNotReadableException exception) {
        ProblemDetail problem =
                ProblemDetail.forStatus(HttpStatus.BAD_REQUEST);
        problem.setTitle("Invalid request body");
        problem.setDetail("Check the JSON syntax and field types.");
        return problem;
    }
}

Import HttpMessageNotReadableException from org.springframework.http.converter. In a production handler, validation details can be converted into a safe list of field errors. Avoid returning raw exception messages: they may expose implementation details or echo submitted input.

7. Optional bodies, forms, and multipart requests

  • Optional body: use @RequestBody(required = false) only when the endpoint contract genuinely allows no body, then handle null explicitly. An optional body does not mean an invalid or empty JSON document is valid.
  • Form fields: use @RequestParam or @ModelAttribute for form submissions rather than treating URL-encoded fields as JSON.
  • Multipart upload: use @RequestPart for a JSON part or file part and configure upload size limits; do not model a multipart request as one JSON body.
  • Large payload: validate limits at the server, reverse proxy, and application layers. Avoid buffering arbitrarily large client-controlled content in memory.
@PostMapping(
    path = "/api/documents",
    consumes = MediaType.MULTIPART_FORM_DATA_VALUE
)
public DocumentResponse upload(
        @RequestPart("metadata") @Valid DocumentMetadata metadata,
        @RequestPart("file") MultipartFile file) {
    return documentService.store(metadata, file);
}

8. Security and reliability practices

  • Prevent mass assignment: accept purpose-built DTOs; never bind arbitrary client fields directly to privileged domain or persistence objects.
  • Enforce request-size limits: configure appropriate limits for JSON and multipart requests at infrastructure and application boundaries.
  • Validate ranges and lengths: cap strings, collections, numeric ranges, and nested object sizes to avoid resource exhaustion.
  • Authorize operations: validation does not establish that the caller may modify the referenced resource.
  • Protect sensitive data: do not log full request bodies by default; redact secrets and personal data.
  • Handle duplicate submissions: for operations that clients may retry, define idempotency behavior where necessary.
  • Use appropriate content types: document supported request formats and return clear client errors for unsupported media types.

9. Test request-body behavior

Controller tests should cover successful deserialization, invalid fields, malformed JSON, missing required bodies, and unsupported media types. MockMvc allows testing the MVC contract without opening a network port.

mockMvc.perform(post("/api/courses")
        .contentType(MediaType.APPLICATION_JSON)
        .content("""
            {"code":"CS336B","title":"OOPS with Java","credits":4}
            """))
    .andExpect(status().isCreated())
    .andExpect(jsonPath("$.code").value("CS336B"));

mockMvc.perform(post("/api/courses")
        .contentType(MediaType.APPLICATION_JSON)
        .content("""
            {"code":"","title":"","credits":99}
            """))
    .andExpect(status().isBadRequest());

Also test nested validation and error response shape. Keep assertions focused on the public HTTP contract rather than Jackson’s internal exception text, which can vary across versions.

Interview questions

  1. What does @RequestBody do?
    It asks Spring MVC to read the HTTP request body and convert it to the declared Java parameter type using a suitable message converter.
  2. What is the difference between Content-Type and Accept?
    Content-Type describes the request body format; Accept lists response formats the client can handle.
  3. How do you trigger Bean Validation on a request DTO?
    Annotate fields with constraints and put @Valid on the @RequestBody parameter, with a validation provider on the classpath.
  4. Why use request DTOs instead of entities?
    They define a narrow API contract and prevent clients from setting internal or privileged fields.
  5. What is the typical difference between malformed JSON and a constraint violation?
    Malformed JSON cannot be deserialized; a constraint violation is a deserialized object that fails declared validation rules.
  6. When is @RequestPart useful?
    For multipart requests where a part may be a file or a separately converted object, such as JSON metadata.
