REST Controller in Spring Boot

Map HTTP requests to Java methods and return clear, validated API responses with Spring MVC.

← Previous: RESTful Web Services Unit 5 Home Next: Request Mapping →

Learning outcomes

After this lesson, you should be able to explain @RestController, map requests to handler methods, bind path/query/header/body data, return appropriate responses, validate input, and handle errors consistently.

Controller responsibility: translate HTTP input into an application call and translate the result into an HTTP response. Keep business rules and persistence logic in service and repository layers rather than growing the controller into the whole application.

1. What is a REST controller?

Spring MVC uses annotated controller classes to handle HTTP requests. @RestController is a composed annotation that combines @Controller and @ResponseBody. As a result, handler return values are written to the HTTP response body and converted by an HttpMessageConverter, rather than being interpreted as view names.

For JSON APIs, Spring Boot commonly configures Jackson-backed converters when the relevant web and JSON dependencies are present:

  • Incoming JSON is deserialized into a Java request type.
  • The controller invokes application logic.
  • A returned Java response type is serialized to JSON.
  • The HTTP response carries a status, headers, and optional body.
import org.springframework.web.bind.annotation.RequestMapping;
import org.springframework.web.bind.annotation.RestController;

@RestController
@RequestMapping("/api/courses")
public class CourseController {
    // Handler methods are declared here.
}

2. Mapping requests to handler methods

Use method-specific annotations such as @GetMapping, @PostMapping, @PutMapping, @PatchMapping, and @DeleteMapping. A class-level @RequestMapping provides a shared path prefix; method-level mappings describe individual operations.

AnnotationHTTP methodExample intent
@GetMappingGETRead a resource or collection.
@PostMappingPOSTCreate a resource or submit a command.
@PutMappingPUTReplace a resource at a known URI.
@PatchMappingPATCHApply a documented partial modification.
@DeleteMappingDELETEDelete a resource.

Mappings can also constrain the request by consumes and produces media types or by request parameters and headers. A request that does not match these conditions may result in an HTTP 4xx response such as 404, 405, or 406, depending on what failed.

3. Bind request data

Spring MVC provides annotations for common parts of an HTTP request:

AnnotationSourceExample
@PathVariableA named path segment./api/courses/{id}
@RequestParamA query parameter or form parameter.?page=0&size=20
@RequestHeaderAn HTTP request header.Accept-Language
@RequestBodyThe request body, converted from JSON or another supported format.JSON create/update request.
@CookieValueA named cookie.Application-specific cookie data.

Use explicit names when they improve clarity. Make optionality clear with required = false or a suitable default value, and validate values at the boundary.

@GetMapping("/{id}")
public CourseResponse getCourse(
        @PathVariable("id") long courseId,
        @RequestParam(defaultValue = "false") boolean includeStudents,
        @RequestHeader(name = "Accept-Language", required = false)
        String language) {
    return courseService.findCourse(courseId, includeStudents, language);
}

4. Return response bodies, statuses, and headers

When a simple fixed status is sufficient, @ResponseStatus can declare it. Use ResponseEntity<T> when the status or headers are determined dynamically, such as a resource creation response with a Location header.

Return a created resource with a Location header

import java.net.URI;

import org.springframework.http.ResponseEntity;
import org.springframework.web.util.UriComponentsBuilder;

@PostMapping
public ResponseEntity<CourseResponse> createCourse(
        @Valid @RequestBody CreateCourseRequest request,
        UriComponentsBuilder uriBuilder) {
    CourseResponse created = courseService.create(request);
    URI location = uriBuilder
            .path("/api/courses/{id}")
            .buildAndExpand(created.id())
            .toUri();

    return ResponseEntity.created(location).body(created);
}

Use 204 No Content when a successful operation intentionally returns no body. Do not return 200 OK with an empty body by habit if a more precise status communicates the outcome better.

5. A small controller with a service boundary

This example demonstrates constructor injection and maps common operations for a course resource. The service and DTO types represent application code and should be defined separately.

package com.example.course.controller;

import java.util.List;

import jakarta.validation.Valid;
import org.springframework.http.HttpStatus;
import org.springframework.http.ResponseEntity;
import org.springframework.web.bind.annotation.DeleteMapping;
import org.springframework.web.bind.annotation.GetMapping;
import org.springframework.web.bind.annotation.PathVariable;
import org.springframework.web.bind.annotation.PostMapping;
import org.springframework.web.bind.annotation.PutMapping;
import org.springframework.web.bind.annotation.RequestBody;
import org.springframework.web.bind.annotation.RequestMapping;
import org.springframework.web.bind.annotation.RestController;

@RestController
@RequestMapping("/api/courses")
public class CourseController {
    private final CourseService courseService;

    public CourseController(CourseService courseService) {
        this.courseService = courseService;
    }

    @GetMapping
    public List<CourseResponse> listCourses() {
        return courseService.findAll();
    }

    @GetMapping("/{id}")
    public CourseResponse getCourse(@PathVariable long id) {
        return courseService.findById(id);
    }

    @PostMapping
    public ResponseEntity<CourseResponse> createCourse(
            @Valid @RequestBody CreateCourseRequest request) {
        CourseResponse created = courseService.create(request);
        return ResponseEntity.status(HttpStatus.CREATED).body(created);
    }

    @PutMapping("/{id}")
    public CourseResponse replaceCourse(
            @PathVariable long id,
            @Valid @RequestBody UpdateCourseRequest request) {
        return courseService.replace(id, request);
    }

    @DeleteMapping("/{id}")
    public ResponseEntity<Void> deleteCourse(@PathVariable long id) {
        courseService.delete(id);
        return ResponseEntity.noContent().build();
    }
}

For a complete create response, add a Location header as shown above. The example uses ResponseEntity to make the status explicit; another controller can use @ResponseStatus(HttpStatus.CREATED) when the status is fixed.

6. Validate request bodies

Use Jakarta Bean Validation constraints on DTO fields and place @Valid before @RequestBody. Include Spring Boot’s validation starter if it is not already part of the application.

import jakarta.validation.constraints.NotBlank;
import jakarta.validation.constraints.Size;

public record CreateCourseRequest(
        @NotBlank
        @Size(max = 20)
        String code,

        @NotBlank
        @Size(max = 120)
        String title
) {}

Validation failures are request errors and should produce a clear 4xx response. Validation is not a replacement for business checks such as ensuring the course code is unique; those checks belong in the application/domain layer and can produce a conflict response.

7. Handle errors consistently

A controller can throw a domain-specific exception when a resource is not found. A shared @RestControllerAdvice can translate it to a stable response across controllers. Spring supports ProblemDetail for standardized HTTP API errors.

import org.springframework.http.HttpStatus;
import org.springframework.http.ProblemDetail;
import org.springframework.web.bind.annotation.ExceptionHandler;
import org.springframework.web.bind.annotation.RestControllerAdvice;

@RestControllerAdvice
public class ApiExceptionHandler {
    @ExceptionHandler(CourseNotFoundException.class)
    ProblemDetail handleNotFound(CourseNotFoundException exception) {
        ProblemDetail problem =
                ProblemDetail.forStatus(HttpStatus.NOT_FOUND);
        problem.setTitle("Course not found");
        problem.setDetail(exception.getMessage());
        return problem;
    }
}

Keep client-facing details safe and useful. Do not return stack traces, SQL errors, secrets, or internal class names. Handle validation failures and expected business conflicts explicitly; log unexpected server errors at an appropriate boundary without logging the same exception repeatedly at every layer.

8. Test controllers

Controller tests should verify the HTTP contract: route, status, headers, request/response serialization, and validation behavior. A Spring MVC slice test can load the web layer without starting the entire application; the service can be replaced with a mock.

import static org.mockito.Mockito.when;
import static org.springframework.test.web.servlet.request.MockMvcRequestBuilders.get;
import static org.springframework.test.web.servlet.result.MockMvcResultMatchers.jsonPath;
import static org.springframework.test.web.servlet.result.MockMvcResultMatchers.status;

import org.junit.jupiter.api.Test;
import org.springframework.beans.factory.annotation.Autowired;
import org.springframework.boot.test.autoconfigure.web.servlet.WebMvcTest;
import org.springframework.test.context.bean.override.mockito.MockitoBean;
import org.springframework.test.web.servlet.MockMvc;

@WebMvcTest(CourseController.class)
class CourseControllerTest {
    @Autowired
    MockMvc mockMvc;

    @MockitoBean
    CourseService courseService;

    @Test
    void returnsCourseAsJson() throws Exception {
        when(courseService.findById(42L))
                .thenReturn(new CourseResponse(42L, "CS336B",
                        "OOPS with Java"));

        mockMvc.perform(get("/api/courses/42"))
                .andExpect(status().isOk())
                .andExpect(jsonPath("$.id").value(42))
                .andExpect(jsonPath("$.code").value("CS336B"));
    }
}

The precise mock-bean annotation depends on the Spring Boot and Spring Framework version in the project; use the supported test-context mocking annotation for that version. Also test invalid bodies, not-found behavior, and response headers for resource creation.

9. Common controller mistakes

  • Returning persistence entities directly: this can expose internal fields or create serialization cycles. Use API response DTOs.
  • Putting business logic in handlers: move reusable rules and use cases into services.
  • Using a path variable for filters: use query parameters for optional filtering and pagination.
  • Ignoring status semantics: distinguish successful reads, creation, no-content operations, validation failures, and missing resources.
  • Accepting unvalidated input: apply syntactic validation and enforce business invariants.
  • Overly broad exception handling: do not convert every failure to 200 OK or reveal internal errors to clients.
  • Ambiguous routes: avoid overlapping mappings that depend on incidental resolution; make path, method, and media type constraints clear.
  • Blocking request threads: keep synchronous handlers bounded and move long-running work to an asynchronous workflow where appropriate.

Interview questions

  1. What does @RestController do?
    It combines controller registration with response-body semantics so handler return values are written to the HTTP response and converted.
  2. What is the difference between @Controller and @RestController?
    @Controller commonly returns view names; @RestController writes return values to the response body by default.
  3. When would you use ResponseEntity?
    When a handler needs to control the response status, headers, and body dynamically.
  4. How does Spring convert a JSON request body into a Java object?
    It uses an HTTP message converter, commonly Jackson-backed in a standard Spring Boot JSON setup.
  5. Why use @RestControllerAdvice?
    It provides centralized exception-to-HTTP-response handling across REST controllers.
  6. What should a controller test verify?
    The externally visible HTTP contract: route, status, headers, serialization, validation, and error behavior.
